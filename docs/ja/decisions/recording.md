# 録画：決定と経緯

録画（録画詳細設計）がなぜ今の形なのか：比べた形式、計測、外したこと。詳細設計には今の動作だけを残し、ここへリンクする。

## 2026-10-28：既定はAV1、なければH.264（録画詳細設計1章、5.1、10章）

**決定（利用者、2026-10-28）：** 録画は、GPUにAV1のエンコーダーがあればAV1、なければH.264とする。利用者はH.264を選べる。H.264のエンコードには、Windows（Media Foundation）とGPUのドライバーのエンコーダーだけを使い、アプリはH.264のエンコーダーを同梱しない。

**理由：**

- H.264には、特許の管理団体（Via LA）を通してライセンスされる特許がある。最後の特許は、アメリカで2027年11月ごろ、ほかの国で2030年ごろまで残る。利用者は、H.264でエンコードするアプリを配布することと、利用者がそれで録画や配信をすることを心配した。AV1は、開発した団体（Alliance for Open Media）が無料で使える特許ライセンスを出している。別の団体（Sisvel）がAV1の特許の管理を名乗っているため、どんな主張もないとまでは言えないが、安全な側である。
- WindowsとGPUのドライバーのエンコーダーを呼ぶ形なら、H.264の実装とそのライセンスは、MicrosoftとGPUのメーカーの側にある。
- 同じビットレートで、AV1はH.264 Highと同じかそれ以上の画質だった（下記）。

**比べて選ばなかったもの：**

- H.265（HEVC）：特許の管理団体が複数あり、H.264より込み入っている。
- VP9：GPUのエンコーダー（NVENC）がエンコードしない。
- H.264だけのまま：特許の心配が残る。

**試作（2026-10-28。試作のプログラムは残していないため、結果をここに記録する）：** 開発PC（Core i7-13700F、RTX 4070、Windows 11）で：

- Media Foundationは「NVIDIA AV1 Encoder MFT」（ハードウェア）を挙げる。録画で使っていたSink Writerのまま、出力の種類だけを変えるとAV1をMP4に書ける。ffprobeはAV1 Mainと読む。
- 1080p30で20秒、実時間でFrameを渡したときの負荷：両方とも同じ。CPUは24スレッドの1.4%、GPUのエンコーダーはH.264で5%、AV1で4.5%。
- 画質：同じ元の映像を6、3、1.5Mbpsでエンコードし、YUVで元と比べた（PSNR、dB）。RGBを通して比べると、コーデックではなく色の変換を測ってしまったため、元の映像をNV12でエンコーダーに渡した。

| 映像 | ビットレート | H.264（既定のプロファイル） | H.264 High | AV1 |
|---|---|---|---|---|
| 細部が多い（フラクタルのズーム） | 6Mbps | 36.7 | 37.5 | 37.9 |
| | 3Mbps | 33.7 | 34.2 | 34.9 |
| | 1.5Mbps | 31.3 | 31.9 | 33.2 |
| 平坦な図形（試験パターン） | 6Mbps | 44.1 | 45.2 | 45.3 |
| | 3Mbps | 40.3 | 40.8 | 40.6 |
| | 1.5Mbps | 37.5 | 38.0 | 38.1 |

- エンコーダーの「画質と速さ」の設定（`CODECAPI_AVEncCommonQualityVsSpeed` 100）はほとんど変わらなかったため、既定のままにする。

**試作で見つかり、合わせて直したこと：**

- プロファイルを指定しないと、H.264のエンコーダーはConstrained Baselineを選んでいた。同じビットレートでHighより約0.5dB悪い。H.264はHighで書くようにした。
- ファイルに色の情報がなかった。プレーヤーは別の色として扱い、いくつかでは暗く見えた。映像にBT.709・limited rangeの情報を付けた。6色の帯を録画してffmpegで読むと、各色の値の差は255に対して3以内だった。

**まだ確かめていないこと：** AV1のファイルが「AV1 Video Extension」の入っていないPCで再生できるか（開発PCには入っている）、AV1のエンコーダーがないGPU（偽のエンコーダーのテストで確かめた）。
