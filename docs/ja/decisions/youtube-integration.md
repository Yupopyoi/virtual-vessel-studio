# YouTube連携：決定と経緯

YouTube APIとの連携（方式設計10.11の「後の段」）を、なぜ今は作らないのか：調べたこと、比べた方法、見送った理由、後で作りやすくするための下準備。

## 2026-11-21：APIでの連携（ログイン、コメントの表示）を見送る（方式設計10.11）

**きっかけ：** 利用者が、配信のコメントを配信画面に出したいと考えた（多くの配信者が外部のツールで行っている）。最初の段として、Googleのアカウントでログインし、自分の配信のコメントを受け取り、配置編集の枠に表示する設計の案を作った。

**決定（利用者、2026-11-21）：** YouTube APIでの連携は、今は作らない。将来、開発者がコメントの機能を作りやすいよう、サービスに依らない下準備（下記）だけを用意する。

**理由：**

- **Googleの審査が要る。** 公式のAPIでログイン（OAuth）を使うには、開発者がGoogle Cloudにプロジェクトとクライアントを登録する。YouTubeのスコープは審査の対象で、審査に通るまでは、同意の画面に「確認されていないアプリ」と出て、使えるのは100人まで。公開の状態が「テスト」の間は、登録したテストユーザーしか使えず、ログインは7日で切れる。審査には、プライバシーポリシーのページ、ホームページ、ドメインの所有の確認、操作の動画が要る。
- **クオータを全利用者で分け合う。** 1日の上限（既定で10,000ユニット）はプロジェクトごとで、本アプリの全利用者の合計になる。
- **悪用を防ぎきれない。** デスクトップのアプリに入れたクライアントIDとシークレットは、取り出せる（Googleも秘密として扱えないとしている）。取り出した人がクオータを使い切ると、全利用者のコメントが止まる。
- 個人で開発し、無料で配るアプリにとって、審査とクオータの管理を続ける負担が大きい。

**調べたこと（2026-11-21、YouTube Data APIの文書）：**

| 項目 | 内容 |
|---|---|
| コメントの受け取り | `liveChatMessages.list`（問い合わせを繰り返す。1回5ユニット）と、`liveChatMessages.streamList`（接続を開いたままにし、新しいコメントが送られてくる。1回5ユニット）。`streamList`はgRPCとHTTPで使える |
| 認可 | `streamList`は、APIキーかOAuthのアクセストークンで使える（文書の例）。自分の配信を探す`liveBroadcasts.list`（`mine=true`）は、`youtube.readonly`、`youtube`、`youtube.force-ssl`のどれかのスコープのOAuthが要る |
| クオータ | 既定で1日10,000ユニット。`list`を5秒ごとに2時間問い合わせると約7,200ユニットで、1回の配信でほぼ尽きる。`streamList`なら1回の配信で約6〜10ユニット（全利用者で1日約1,000回） |
| デスクトップのOAuth | ループバックのリダイレクト（`127.0.0.1`）とPKCE。アプリの中のWebViewは使えない（既定のブラウザーを使う） |
| Unityでの通信 | UnityのMonoの`HttpClient`はHTTP/2を使えないので、gRPCは使えない。HTTPの`streamList`でのメッセージの区切り方は文書になく、試作で確かめる必要があった |

**作った設計の案の要点**（作るときの出発点として残す。全文はこの記録を足したブランチの履歴にある）：

- ログイン：ループバックとPKCE、スコープは`youtube.readonly`だけ。保存するのはリフレッシュトークンだけで、Windowsの資格情報マネージャーへ（ストリームキーと同じ）。ログアウトでGoogleの側でも取り消す。
- 配信がLiveになると、`liveBroadcasts.list`で自分の配信を探し、`streamList`でコメントを受け取る。切れたら間を空けてつなぎ直す。
- コメントはただの文字として描く（Rich Textとして解釈しない）。制御文字と書字方向を変える文字を除き、長さに上限、NGワード。アイコン画像は読み込まない。
- 視聴者の名前とコメントは、ディスクにもログにも残さない。
- クライアントIDとシークレットはリポジトリに置かず、リリースのビルドにだけ埋め込む（フォークがクオータを使わないため）。
- YouTube APIの型は、Streaming Moduleの中に閉じ込める。

**比べて選ばなかったもの：**

- APIキーをアプリに入れ、利用者が配信のURLを貼る方法：ログインは要らないが、クオータの共有と、キーが取り出されて悪用される問題は同じ。
- 利用者が自分のGoogle Cloudのプロジェクトを作る方法：審査もクオータの共有もなくなるが、通常の利用者に開発者向けの手順を求めることになる（CLAUDE.md 3.1）。
- 非公式な方法（YouTubeのページの解析や、内部のAPI）：ログインもクオータも要らないが、YouTubeの利用規約に反し、予告なく壊れる。

**今使える代わりの方法：** 同じPCのウィンドウの取り込み（Capture詳細設計）で、ブラウザーに開いたYouTubeのポップアウトチャットのウィンドウを取り込み、配置編集で配信画面に置く。ログインもクオータも要らず、YouTubeの公式のページを映すだけである。見た目はチャット欄のままで、NGワードでの絞り込みはできない。

**下準備（将来コメントの機能を作りやすくするため。作る時期は利用者が決める）：**

サービスに依らない部分だけを作り、YouTubeやGoogleのコードは入れない。後でYouTubeやTwitchの受け取りを加えるとき、受け取りの部分を1つ書けば表示まで動くようにする。

1. コメントの型と流れ：`LiveChatMessage`（ID、時刻、名前、本文、種類、配信者か、モデレーターか、メンバーか）と`ILiveChat`（状態、最近のコメント、受け取りの開始と停止）。
2. 絞り込み：制御文字と書字方向の文字の除去、長さの上限、NGワード（純粋関数）。
3. 表示：コメントを描画用のTextureへ描くもの（UI）と、配置編集のコメントの枠（Stage。アバターの枠と同じ`IFrameSource`）。
4. 試しの受け取り：開発者モードで、決まった文や手で打った文をコメントとして流すもの。受け取りがなくても、表示と枠を確かめられるようにする。

**再び検討するときに要ること：**

- 利用者（開発者）の名義のGoogle Cloudのプロジェクトと、審査の申請（プライバシーポリシー、ホームページ、ドメイン、動画）。
- クオータの増加の申請の方針。
- HTTPの`streamList`の区切り方の試作。使えなければ、ネイティブのWinHTTP（HTTP/2）でgRPCを話す方法。
- YouTube API Services Terms、Developer Policiesの、表示と保存の条件の確認。
