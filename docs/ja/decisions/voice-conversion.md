# 音声変換：決定と経緯

リアルタイム音声変換の試作で試したことと、その結果の記録。Voiceの詳細設計はまだない。試作の結果をもとに作る。

## 2026-11-01 Unity内のリアルタイムRVCの試作（方式設計9.5、9.10）

### 目的

方式設計9.5は、RVCをUnity Inference Engineで動かし、200 ms以内を基準とする。Audio詳細設計8.3の処理の段として実際の経路に載せて、これが成り立つかを確かめた。

### 測定の条件

- RTX 4070、Unity 6000.6.4f1のEditor（Mono）、`com.unity.ai.inference` 2.6.1、GPUCompute
- 入力はVoxCPM2で作った男声（基本周波数の中央値115 Hz）の12秒のWAV。変換先はVoxCPM2で作った女声441秒で学習したRVC v2（40 kHz、150エポック、インデックスなし）。移調は+13
- 数値は録音した音声での測定である。実際のマイクとモニターでは、利用者が聞いて確認した（2026-11-01、話者を入力にしたモデルを含む）。「概ね良好」「ひとまずは問題ない」。遅延は今後の改善の対象である

### VCBMから変えたこと

VCBMは2秒の窓を重ねて変換する。これはWAVのバッチ変換の形なので、RVC本家のリアルタイム実装（`infer/rtrvc.py`）の形に変えた。

| | VCBM | 試作 | 理由 |
|---|---|---|---|
| HuBERT | 2秒 | 1秒 | 特徴量の文脈はこれで足りた（話者の類似度が落ちない） |
| RMVPE | 224フレーム | 32フレーム、音高をキャッシュ | 本家と同じ。ブロックごとに全体を推定しない |
| 生成器 | 窓全体 | Flowは末尾、デコーダーは1ブロック分 | 本家と同じ。重いボコーダーをブロック分だけ動かす |
| つなぎ方 | 固定の重ね合わせ | 相関で位置を合わせるクロスフェード | 本家と同じ。音量は相関で補正した |

RMVPEのGRUを展開するVCBMの書き出しは、そのまま使っている。Inference EngineにGRUがないためである。

### 処理時間

ブロックを1つずつ完了まで待った場合（100 ms、ms）：

| 段 | 中央値 |
|---|---|
| 全体 | 50.7（最大60.0） |
| うちGPU待ち | HuBERT 9、RMVPE 21、生成器 8 |
| うちメインスレッドで発行 | 約18（RMVPEが8.4） |

実時間で60 Hzのフレームループに載せた場合（`VoiceServiceRealtimeBenchmark`、20秒）：

| 項目 | 結果 |
|---|---|
| 処理したブロック | 199、取りこぼし0 |
| 1ブロックの処理 | 中央値85.9 ms、最大90.3 ms |
| 通常のフレームの負担 | 0.1 ms |
| 発行するフレームの負担 | 約17 ms、最大22.5 ms |

処理が待つ場合より長いのは、発行、RMVPEとHuBERTの読み出し、生成器の読み出しがそれぞれフレームの区切りを待つためである。

### 遅延：基準を満たしていない

入力の1サンプルが出力されるまで、**約270 ms**かかる。ブロック100 ms、処理86 ms、ファイル上の遅れ85 ms（クロスフェードと余白61 ms、バーストの余裕30 ms）の合計である。ここに機器のバッファーが加わる。基準の200 msを超えている。

候補（どれも未測定）：

- 末尾の余白を30 msから10 msにする：-20 ms。つなぎ目の音量の揺れが増える（次節）
- ブロックを50 msにする：-50 ms。待つ測定では処理が49 msで、実時間では間に合わない見込み。ブロックを重ねて走らせる必要がある
- フレームの区切りを待たない経路にする：GPUの発行がメインスレッドに限られることが制約である

### 音質

Speechbrain ECAPAの話者類似度（変換先の声との）と、入力との音高の相関：

| | 話者類似度 | 音高の相関 |
|---|---|---|
| RVC本家のオフライン変換 | 0.881 | 0.996 |
| 試作（ブロックごとに待つ） | 0.885 | 0.995 |
| 試作（実時間） | 0.886 | 0.993 |
| 参考：学習データそのもの | 0.836 | - |
| 参考：入力の声 | 0.260 | - |

### 分かったこと

- ブロックの先頭で音量が約2 dB下がる。原因の候補を順に確かめた：デコーダーの端に余白を足す→変わらない。ノイズを時刻に結びつけ、クロスフェードの音量を相関で補正する→変わらない。末尾の余白を10 msから30 msにする→-2.3 dBから-1.6 dBへ改善し、10 Hzの揺れは半分になった。窓の末尾の特徴量が弱いことが原因の一部と見ている。実時間の出力では-1.2 dBが残っている。**聞いて判断する必要がある**
- `ReadbackRequest`の結果は、完了したフレームの間しか読めない。遅いモデルを待ってからまとめて読むと、速いモデルのデータが消えて例外になる。それぞれ完了した時点で読む
- 非同期の読み出しは、EditModeのバッチ実行では確かめられない。実時間のベンチマークはPlayModeで実行する

### 試し方

モデルと音声はリポジトリの外にある。`.sentis`をData Rootの`VoiceModels/Prototype`に置き（`hubert_16000`、`rmvpe_32`、`gen_b10`と話者の`gen_b10.spk`）、開発者モードの診断画面の「声の変換（試作）」で有効にする。「音声ファイルを流す」を使うと、声を出さずに、録音（WAV、M4A、MP3）をマイクの代わりに実時間で変換できる。M4AとMP3はAudioのプラグインがWindowsのデコーダーで読む（Audio詳細設計5.4）。マイクの行の「聞く」とモニターの機器が必要で、配信と録画にも流れる。プラグインを更新したあとはEditorの再起動が必要である。

## 2026-11-01 Editorなしで声の`.sentis`を作る

ONNXを`.sentis`にする変換はUnity Editorにしかなく、配布したアプリでは使えない。声が違ってもモデルの構造は同じなので、重みだけを差し替えられるかを検証した。

### 方法

Inference Engineの`Constant.array`は`internal`で、公開APIでは書き換えられない。そこで`.sentis`の中の重みのバイト列を直接書き換える。

1. 開発者がEditorで、事前学習モデルからひな形の`.sentis`を作る
2. ひな形と1つの声から、各重みのファイル内の位置を表にする（`tools/voice/weight_manifest.py build`）
3. 学習が終わった利用者のPCで、学習済みの重みをその位置に書く（同`apply`）。Pythonだけでよく、1.3秒

### 結果

**配置表を作るのに使っていない声で、EditorとPythonの結果がSHA-256で完全に一致した。** 352個の重みすべての位置が分かった。作った声をUnityで変換すると、話者類似度は0.888、音高の相関は0.995で、Editorで変換した声と同じである。実時間で199ブロックを取りこぼしなく処理した。

### 分かったこと

- 話者を固定すると、条件づけの重みが読み込み時に定数へ畳み込まれ、差し替えられない。**話者ベクトルをモデルの入力にする**。重みは`.spk`に分けて持つ
- `emb_rel_k`は転置され、窓の長さまでパディングされて入る。窓の長さを変えると配置表も作り直す
- 数バイトの重みは別の場所と偶然一致する。配置表を作るときに、Editorの結果にその値があることも確かめる

### 注意

`.sentis`の形式は公開された仕様ではない。`com.unity.ai.inference`を更新したら、ひな形と配置表を作り直して、この比較を再び行う。

## 2026-11-01 音を長く伸ばしたときの揺れ

利用者の報告：話している間は問題ないが、音を長く伸ばすとおかしくなる。

実際の録音の持続音で、音量と高域の揺れを測った（値は小さいほど安定している。ばらつきの指標）。

| 方法 | 音量 | 音色 |
|---|---|---|
| RVC本家のオフライン変換 | 0.126 | 0.197 |
| RVC本家のリアルタイム（既定、履歴2.5秒） | 0.251 | 0.418 |
| RVC本家のリアルタイム（履歴5.36秒） | 0.143 | 0.377 |
| Unity（窓1秒） | 0.231 | 0.417 |
| Unity（窓5.4秒。のちに取り消し、次の節） | 0.126 | 0.356 |

音高は安定していて、原因は音量と音色の揺れだった。本家のリアルタイムでも同じように揺れるので、実装の誤りではなく短い文脈で動かす性質である。話している間は音が変わり続けるので隠れる。

本家で履歴を長くすると安定し、以前の試作のメモ（5.36秒の履歴）と一致した。HuBERTだけ長くしても0.207で足りず、生成器にも長い文脈が要る。音色は改善が小さく、オフラインとの差が残る。

Unityでの費用：待った場合の処理は1ブロック51 msから72 msへ増えたが、実時間では発行がフレームに揃うので85 msのままで、取りこぼしは0、遅延も増えない。

効果が確認できなかったこと：正弦波の位相を連続させる（Unityで測定）。自作のPythonのシミュレーションでの比較（特徴量の時間平均、index、ノイズの固定など）は、シミュレーションが実物と合わず、確かな結論ではない。検証には本家のコードを使うべきだった。

本家の測定でCUDA Graphが古いグラフを再生し、条件の変更が効かないことがあった。`run_cuda_graph`を外して測り直した。

## 2026-11-02 窓5.4秒の訂正と、2段の並列化

前の記録の「窓5.4秒を採用」は誤りだった。利用者が聞くと、話している間にブツブツと途切れ、持続音も改善していなかった。アプリの終了時の集計では、マイクの音切れが約3分で1608回（窓1秒の以前の回では1〜8回）あった。ベンチマークは映像、トラッキング、アバターが動いていないEditorで測っていて、GPUの取り合いを再現していなかった。窓を1秒に戻した。

ベンチマークを作り直した：フレームを20から36 ms（アプリのログの値）にばらつかせ、毎フレーム別のモデルをGPUで動かし、ミキサーの規則（20 msたまったら再生、10 msずつ取り、尽きたら捨てて待つ）で音切れを数える。この条件で、20秒のうちの音切れは窓1秒で119回、2.5秒で120回、5.4秒で140回になり、問題を再現できた。

原因は処理の進め方だった。1ブロックの3段（HuBERTとRMVPE、生成器、受け取り）を順に、それぞれフレームの区切りを待って進めていたので、フレームが長いと1ブロックに100 msより長くかかる。GPUの使用率は47%で、性能には余りがあった（利用者の確認）。

次のブロックのHuBERTとRMVPEを、このブロックの生成器と同時に動かすようにした。

| 窓 | 並列化の前 | 並列化の後 |
|---|---|---|
| 1秒 | 音切れ119回、取りこぼし26 | 音切れ1回、取りこぼし0 |
| 2.5秒 | 120回、26 | 0回、0 |
| 5.4秒 | 140回、36 | 0回、0 |

この負荷では1ブロックに115から122 msかかるので、遅延は約0.3秒になる見込みである。この負荷は実際のアプリより重いようで、窓1秒でも以前より多く途切れている。

窓は診断のCardで1、2.5、5.4秒から選べる。どれが聞いてよいかは利用者の確認を待つ。終了時の集計に、1ブロックの時間（`Voice/BlockWork`）と取りこぼし（`Voice/DroppedBlocks`）が出る。

今後、改善の判断は、アプリの終了時の音切れの回数と、利用者が聞いた結果で行う。ベンチマークの数字だけで改善したと報告しない。

## 2026-11-02 GPUとの往復を1回にする

## 2026-11-03 長く伸ばした声がノイズ除去で消える

利用者がアプリで確かめた（窓5.4秒、ノイズ除去オン）。長く伸ばすと、声を出し続けているのに無音になった。録画では、出力がだんだん小さくなってから消えていた。

| | 伸ばした声 | 間の雑音 | 話し声の音量 |
|---|---|---|---|
| RNNoiseだけ | 2秒で-48 dB | -30.1 dB | -2.1 dB |
| 元の音を戻す | 最後まで入力と同じ | -29.1 dB | -1.1 dB |

声がある間は、声に重なった雑音も残る。利用者が聞いての確認はまだである。

## 2026-11-03 ノイズ除去が、伸ばした声の中に短い途切れを作る

同じ録音の3回目の伸ばしでは、ノイズ除去だけを通しても短い途切れが残っていた。10 msごとに見ると、ところどころで10〜56 dB下がる（伸ばしの後半では、1秒ごとの音量が2.5〜3.9 dB下がる）。どの途切れも100 msより短いので、上の100 msごとに12 dB下がるかの比較では見つからなかった。聞くと、声がぶつぶつ切れる。

対策：声があった最後のフレームから100 msは重ねる割合を保ち、そのあとはこれまでどおり下げる。録音と、雑音（-40 dBFS）を足した話し声で、シミュレーションで測った：

| 保つ時間 | 伸ばした声の中で最も下がった100 ms | 間の雑音（すべて） | 300 msより長い間の雑音 |
|---|---|---|---|
| なし（直す前） | -59.0 dB | -30.1 dB | -46.7 dB |
| 50 ms | -2.0 dB | -15.8 dB | -46.7 dB |
| 100 ms（採用） | 0.0 dB | -12.8 dB | -46.7 dB |
| 200 ms | 0.0 dB | -8.7 dB | -46.7 dB |

ビルドしたプラグインでは、録音の伸ばした声のどの1秒も入力と同じ音量を保つ。雑音が多く残るのは、声のすぐあとの音節の間の短いすき間だけで、本当の間ではこれまでどおり消える。音量が下がったとき（6、10、15 dB）にも割合を下げる保ち方は、結果が同じだったので採らなかった。

アプリの負荷のあるベンチマークはノイズ除去を通さない。なので上の、変換した3回目の伸ばしが10〜15 dB小さくなる件は、入力の声がかすれるところでの変換そのものの問題で、これでは直らない。利用者が聞いての確認はまだである。

## 2026-11-03 長く伸ばした声の途中で、母音が変わる

利用者が、長く伸ばした声の途中で母音が変わって聞こえると言った。録音の2回目の伸ばし（「い」）では、入力の第2フォルマントはずっと約2,600 Hzだった。変換した声では、窓5.4秒で伸ばし始めて約3秒後に約3,100 Hzから約1,450 Hzに下がり（「う」や「お」寄り）、窓1秒ではほぼすぐに下がった。

## 2026-11-03 「う」がまだ「あ」に寄る。伸ばした声を見本にする方法は試して採らない

HuBERTは、周りの音と比べて母音を判断する。上流で「う」だけを変換すると正しかったが、前に話し声を1〜12秒置くと「あ」に寄り、雑音でも寄った。利用者の伸ばした「あ」「い」を0.7秒ずつ前に置くと、「う」はずっと正しかった。見本のために5つの母音を録ってもらう案は見送った。利用者は、ユーザーに何かを頼むことをしたくない。

試したこと：利用者が最後に伸ばし終えた3つの声（0.7秒ずつ、自動で集める）と、直近の話し声1秒を、3.1秒の見本にする。HuBERTの特徴では良く見えたが、変換した声では良し悪しが分かれた：

## 2026-11-03 声を設計する実験

目的：利用者が自分好みの声を作り出せる仕組み（Voice Lab詳細設計8.3）の各段階が成り立つかを確かめる。手順と音声はリポジトリの外（voice-work）にある。

1. 土台：VCBMのつまみ式の指示文（`VoicePromptBuilder`）で6通り×乱数2つの候補を作った。乱数の影響がつまみより大きい（同じ指示で268 Hzと406 Hz）。利用者は以前にも、つまみでは理想に届きにくかったと記憶している。利用者はairy_soft（乱数101）を選び、もっと高く、幼く、舌足らずに、元気に、と求めた。
2. 言葉の指示で寄せる：土台を手本にした指示は声らしさを保つ（話者の特徴量ECAPAの類似度0.90〜0.95。候補どうしは中央値0.64）が、効くかは乱数次第だった。生成した声を手本に重ねると、声が枯れた（利用者が聞いて判断。倍音と雑音の比HNRは22.5 dBから15〜21 dBへ下がった）。拡散のステップを10から25にすると少し澄む。
3. 実在の声のサンプルから作る案は、権利の問題がない声の当てがないので、やめた（利用者の判断）。
4. 波形の加工：WORLDで高さ、響き、抑揚、息、速さを数値で動かした。合成し直しの劣化は気にならない（利用者）。+4半音・響き×1.10は「同じ人と言えば同じ人」。抑揚を1.6倍、2.0倍にすると機械っぽくなる（利用者）。
5. 学習と変換：土台の声のコピー7.5分を作り、そのままのものと、+4半音・響き×1.10に加工したもので、それぞれRVCを学習した（各約11分）。利用者の話し声を変換すると、どちらも自分が学習した声色に近く、もう一方からは離れた：

| 学習 | 加工なしの声との類似度 | 加工した声との類似度 |
|---|---|---|
| 加工なし | 0.72〜0.80 | 0.30〜0.41 |
| 加工あり | 0.32〜0.46 | 0.70〜0.80 |

加工した声色は、学習と変換を通っても残る。利用者の評価は「及第点」。ただしこの変換は上流のファイル全体の変換で、リアルタイムの変換では確かめていない。上流の変換は窓の問題を隠すので、作った声はリアルタイムの経路で評価する（Voice Lab詳細設計8.3.4）。

分かったこと：声色（響き、年齢の感じ、息っぽさ）は学習したモデルから、抑揚、速さ、発音の癖は話す本人から来る。入力の声の高さの中央値から移す量を決めると、話し声ごとの高さの違いを吸収できた。

## 2026-11-03 VoxCPM2の依存を絞り、環境を1つにできるか確かめる

Voice Labの実装の前に、未検証だった2点を確かめた（Voice Lab詳細設計17章）。

**ライセンス**：`voxcpm` 2.0.3のパッケージはApache-2.0、モデル（Hugging Faceの`openbmb/VoxCPM2`、revision `32279effe8c1`）もApache-2.0である。モデルカードは、なりすまし、詐欺、偽情報への利用を禁じ、AI生成物の明示を求める（既に記録済みの利用条件と同じ）。

**依存を絞る**：`voxcpm`を依存なしで入れ、推論のコードが読み込むものだけ（torch、torchaudio、transformers、tokenizers、huggingface_hub、safetensors、einops、pydantic、numpy、librosa、soundfile、tqdm）を入れた。

- 153パッケージが65になった。`funasr`、`kaldiio`（NTTの評価用使用許諾）、`modelscope`、`datasets`、`gradio`、`torchcodec`は入らない。
- 同じ手本と乱数で作った音声は、元の環境とサンプル単位で一致した。
- 残るライセンスの注意は`soxr`（LGPL、既に差し替え可能な形で使うと決めた）だけである。ライセンスの全文の検索では、`numpy`、`scipy`、`torch`の同梱の部品の一般的な条文のほかに該当はない。
- 学習用（`voxcpm/training`）と雑音除去（`zipenhancer`、ModelScope）は使わないので、それらの依存は入れない。`normalize=True`の文の正規化（`wetext`、`inflect`）も使わない。

**RVCと同じ環境**：学習環境の版（Python 3.12、torch 2.7.1+cu118、numpy 1.26.4、transformers 4.49.0、librosa 0.10.2）に`voxcpm`と`einops`、`pydantic`を足した環境でも、VoxCPM2は動いた。

- 同じ乱数でも波形は一致しない（版が違うと生成の途中が変わる）。声は同じで、話者の類似度0.988、声の高さの中央値は326 Hzと327 Hzだった。
- 候補を同じ乱数で作り直せるのは、同じ版の環境の中だけである。候補の条件と一緒に、環境の版を残す。
- RVCの学習がこの環境で今までどおり動くかは、まだ確かめていない（足すのは`einops`、`pydantic`、`voxcpm`だけで、RVCの依存の版は変わらない）。

1つの環境にできれば、構築の手間と容量（torchとCUDAで数GB）が1回分で済む。

## 2026-11-05〜2026-11-06 声色を寄せる：何が声を動かすか、どこまでか

目的：ユーザーが分かって使え、本当に声が変わる操作を見つける（Voice Lab詳細設計8.3.1、8.3.2）。どの試験も、同じseedで作るか、同じ2つの声（約257 Hzと321 Hz）をWORLDで編集し、編集なしで作り直した声と音量をそろえて比べた。スクリプトと音声はリポジトリの外（voice-work）にある。

1. **雰囲気と高さ**：指示文は境目でしか変わらないので、雰囲気のスライダーを名前付きの段階にした。各6つのseedで、高さの「低め」〜「やや高め」は同じ中央値（約260 Hz）、「高め」で約300 Hz、若さと高さを合わせて約+60 Hz、若さ「大人の女性」で約-30 Hz。ことばにHzを書いても効かなかった。約370 Hzより上は出なかった。「アニメ風」寄りに組み合わせると、無理している感じのことがあった（ユーザー）。
2. **選んだ候補の近くの候補**（選んだ声をVoxCPM2の手本にする）：3回つないでも自然だった（ユーザー）。1回の6個ははっきり違う。STEP 1では同じ人の声を保つ必要はない（ユーザー）。
3. **広い帯域**（1.5オクターブの帯域を6または12 dB上げ下げ）：違いは小さい（ユーザー）。
4. **番号で選んだ倍音と狭い帯域**：第2倍音から上と、1.4 kHzから上の1/3オクターブは設定どおり動いたが、違いはやはり小さかった。第4・第5倍音（この声で約1〜1.3 kHz）を動かすと、こもる、鼻にかかるように聞こえた。
5. **明るさ**：前のつまみ（1 kHzを軸に24 kHzまで続く傾き）は、+3で8 kHzより上がエネルギーの44%になり（元は1.3%）、雑音に聞こえた。2〜5 kHzを8 dB上げると明るいが少しかすれた。倍音だけを上げ、雑音の大きさを保つと、かすれずに明るさが残った（ユーザー）。1 kHzより上の共鳴を上へずらす（「笑顔」）は、あまり変わらなかった。
6. **高さと明るさ**：+4半音は、年齢+4より明るく聞こえた。高さ+4だけ、またそれに明るさを足したものは許容。高さ+4、年齢+4、明るさを全部重ねると機械っぽかった（ユーザー）。
7. **やわらかい／張った**：倍音を番号に沿って傾けると、やわらかい側は鼻声、張った側はとげとげしかった（張った側はやめた）。第1倍音だけを上げると鼻声にならずにやわらかく、4 kHzより上を下げるときつさが取れた。息の量を一緒に変えても、あまり変わらなかった。STEP 1の雰囲気「やわらかさ」は、聞くとやわらかい候補を作った。やわらかさの目安として知られるH1−H2は、ある候補で耳と食い違ったので、判断には使わない。

決めたこと（ユーザー、2026-11-06）：明るさは2〜5 kHzの倍音を上げる（+6で8 dB）。やわらかさ（0〜+6）は第1倍音を最大6 dB上げ、4 kHzより上を最大3 dB下げる。張った側は作らない。明るさとやわらかさが学習と変換を通っても残るかは、確認中である。
