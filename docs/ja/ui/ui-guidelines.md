# UI Guidelines

## 1. 目的

本書は、画面やComponentを作るときに守るルールを定める（方式設計14.37）。開発者とClaude Codeの双方が対象である。

見た目の値は`design-system.md`、部品の仕様は`components.md`で定める。

---

## 2. 作業の前に

1. `design-system.md`と`components.md`を読む。
2. `docs/assets/ui/styleboard.html`をブラウザで開き、見た目を確認する。
3. 既存の共通Componentで画面を組み立てられるか検討する。

---

## 3. 守ること

1. 値は`design-system.md`のTokenのみを使う。画面ごとに色、文字サイズ、余白を決めない。
2. 共通Componentを優先して使う。新しい見た目が必要な場合は、先に`components.md`へ追加する。
3. UI文字列をC#やUXMLへ直接書かず、Localization Keyを使う（方式設計14.6）。
4. Fontを個別に指定せず、Typography Styleを使う。
5. 日本語と英語の両方で表示を確認する。英語は文字が長くなりやすいため、文字切れや折り返しを確認する。
6. Runtimeの状態を正とし、UIはそれを表示する。UI上の状態をRuntimeの状態として扱わない（方式設計14.29）。
7. UIからRuntimeの機能を直接操作せず、Command等の境界を通す。
8. 利用者向けのエラーと開発者向けの診断情報を分ける。通常の画面にProcess ID、Port、Python等の内部情報を表示しない（方式設計4.27）。
9. 状態は色だけで伝えない。形のアイコンと文字を必ず付ける（`design-system.md` 9.1）。
10. 新しいデザインのパターンを追加した場合は、`design-system.md`または`components.md`と見本ページへ反映する。
11. 実装後はスクリーンショット等で表示を確認する（方式設計14.35）。主要な画面と大きな変更は、利用者が最終確認する（方式設計14.36）。

---

## 4. 文章の書き方

- 利用者に見える言葉で書く。内部の仕組みの名前を使わない（例：「Webhook設定」ではなく「通知」）。
- ボタンには、押すと何が起きるかを動詞で書く（例：「配信を開始」「録画を停止」）。
- エラーは、何が起きたかと、どうすればよいかを書く。謝罪やあいまいな表現は使わない。
- ツールチップは1文で、その操作で何が起きるかを書く（`components.md` 3.12）。
- 日本語と英語で意味を一致させる。どちらかだけに情報を足さない。

---

## 5. 表示の確認

UIを変更したときは、少なくとも次の組み合わせで表示を確認する。

| 項目 | 確認する内容 |
|---|---|
| 背景 | ダーク、ライト |
| 言語 | 日本語、英語 |
| パレット | 既定（Lavender）と、明るいアクセント色のパレット（Lemon等）1つ |
| 色の見え方 | 赤緑、青黄、白黒で状態が区別できること |
| 状態 | 通常、ホバー、選択中、無効、読み込み中、エラー |
| 大きさ | UIの拡大時に文字が切れないこと |
| 操作 | キーボードだけで操作できること |
